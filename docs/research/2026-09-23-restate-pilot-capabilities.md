# Restate capabilities and boundaries for a larger pilot

Date: 2026-09-23. Primary-source research against current upstream documentation and this checkout. This is an evaluation note, not an adoption decision or proof from fault-injection tests.

## Starting point in this repository

- The lockfile resolves TypeScript SDK, Zod integration, and testcontainers to **1.17.1**, and the server to **1.7.10**; manifest ranges use carets. The shared test harness also selects server image 1.7.10. Current documentation can describe optional features that these packages do not enable automatically. [Package manifest](../../package.json), [lockfile](../../package-lock.json), [harness](../../src/__tests__/restate/harness.ts).
- The endpoint binds `Operator` and `orchestratorTools`, with no run workflow registered. Some early paragraphs in `docs/restate.md` still describe an empty service set. Code is the stronger evidence for current wiring. [Endpoint](../../src/restate/endpoint.ts), [existing documentation](../restate.md).
- ADRs 017/018 keep SQLite as run-history authority and propose incremental run-kind migration, including a CI feedback-loop experiment. ADR 023 colocates Restate and the SDK endpoint on one machine; ADR 025 adds an identity object outside run-kind migration. These remain Proposed. [ADR 017](../adr/017-move-the-run-lifecycle-onto-a-durable-execution-engine.md), [ADR 018](../adr/018-adopt-restate-one-run-kind-at-a-time.md), [ADR 023](../adr/023-run-the-restate-server-as-an-orchestrator-sidecar.md), [ADR 025](../adr/025-mcp-tools-are-restate-handlers-and-the-operator-object-is-the-refresh-authority.md).

## What the pilot can reasonably delegate

| Concern | Upstream capability | Implication for this pilot |
| --- | --- | --- |
| Multi-step progress | Journaled operations replay recorded results after failure. Restate-to-Restate calls have integrated idempotency. [Request lifecycle](https://docs.restate.dev/guides/request-lifecycle) | Express dispatch, callback wait, decision, deadline, and conclusion as a workflow. Ordinary external HTTP calls need a separate safety contract. |
| Per-PR races | Exclusive Virtual Object handlers serialize writes per object key; shared handlers can read concurrently. [Handlers](https://docs.restate.dev/foundations/handlers) | A short PR coordinator can admit attempts and reject stale generations. It cannot serialize legacy dispatchers that bypass it or enforce a global worker budget. |
| Long-lived runs | A workflow has one `run` execution per key and concurrent shared interaction handlers. [TypeScript services](https://docs.restate.dev/develop/ts/services) | Give each attempt a durable identity, including the intended head/generation. Reusing a PR number as the only workflow key prevents expressing distinct runs cleanly. |
| Callbacks | Awakeables and named workflow promises are one-shot and survive restarts. Workflow promise results remain readable during retention. [External events](https://docs.restate.dev/develop/ts/external-events) | A shared callback handler can resolve an attempt's promise. Authenticate and validate attempt/head identity before resolution; choose explicit duplicate and conflicting-report behavior. |
| Diagnosis | UI, CLI, and SQL expose invocation status, journal, queues, and blocking object calls. [Introspection](https://docs.restate.dev/services/introspection) | Carry PR, attempt, dispatch, provider-run, and Restate invocation IDs across both systems. SQLite remains useful for product-facing history. |

**Avoid the callback deadlock:** an exclusive object handler keeps its serialization slot while awaiting an awakeable. An exclusive callback to that same object queues behind it. Use the workflow's shared callback handler, or release the coordinator promptly after starting a separate attempt workflow. Shared handlers cannot mutate ordinary object state; they are not a second exclusive writer. [External events](https://docs.restate.dev/develop/ts/external-events), [handlers](https://docs.restate.dev/foundations/handlers).

## Work that remains ours

**External effects and SQLite writes.** `ctx.run` records a returned result; it is not a transaction with another system. Upstream's database guide explicitly describes the window where a successful external update is repeated because its completion was not recorded, and demonstrates conditional updates and transactional idempotency tokens. Thus, wrapping GitHub Actions dispatch, Fly creation, a paid LLM request, a Git push, or a SQLite write does not by itself prove exactly-once effects. This inference follows the same external-effect boundary. Use provider idempotency where available, durable operation IDs, conditional writes, or a defined reconciliation/ambiguity policy. Test a crash after provider acceptance but before the workflow records success. [Database integration](https://docs.restate.dev/guides/databases), [durable steps](https://docs.restate.dev/develop/ts/durable-steps).

**Workspace recovery.** Restate records operation results and its own state, not a runner filesystem snapshot. A recorded “clone completed” result does not recreate a deleted checkout. Keep repository work inside an existing worker attempt, or explicitly persist commits/artifacts and restore the workspace at restart boundaries. This is an architectural inference from the journal/replay contract. [Request lifecycle](https://docs.restate.dev/guides/request-lifecycle).

**Cancellation and deadlines.** Cancellation is cooperative, requires a reachable endpoint, and surfaces at an await boundary. In-progress `ctx.run` work can finish before cancellation is surfaced; detached sends continue independently. Provider job cancellation, cleanup, and late-report rejection therefore need explicit application logic. A timer expiring is not evidence that a runner stopped. [Managing invocations](https://docs.restate.dev/services/invocation/managing-invocations). The default inactivity timeout is one minute; the abort timeout is another setting, not the business deadline. Prefer dispatch-and-wait over holding a long opaque worker call in one step. [Configuration](https://docs.restate.dev/services/configuration).

**Capacity.** Current upstream scope-based flow control is opt-in/preview and requires experimental protocol-v7 and vqueue flags. Limits apply per scope, and unscoped calls bypass them. The sidecar source does not set those flags, although it inherits environment variables; deployed configuration was not inspected. Keep existing shared admission control until the pilot proves ownership of all competing paths and verifies whether invocation concurrency represents actual external worker occupancy. [Flow control](https://docs.restate.dev/services/flow-control), [sidecar](../../src/restate/server.ts).

## Deployment and durability gates

1. **Replay-safe upgrades need a concrete deployment strategy.** Upstream pins invocations to immutable endpoints; old endpoints remain until drained. Replacing code at one endpoint can break replay even when the service schema stays unchanged. The current `register()` checks drain only on a `META0004` conflict before forcing registration. Its `getInFlightJobs()` actually selects all dispatched/running SQLite jobs, despite kg-refresh-specific comments. It does not inventory queued, suspended, or other active Restate invocations. A larger pilot needs either comprehensive admission freeze/draining before replacement or versioned endpoints. A successful no-force registration is not a code-compatibility proof. [Versioning](https://docs.restate.dev/services/versioning), [registration](../../src/restate/endpoint.ts), [job query](../../src/log.ts).
2. **Process recovery is not high availability.** A single node persists with write-ahead logging and fsync; backup requires an atomic view of the base directory plus effective configuration. Restore requires exclusive ownership. Colocating SQLite and Restate adds an application requirement to recover both consistently and reconcile any external effects after the recovery point. [Backups](https://docs.restate.dev/server/snapshots). A one-replica cluster cannot tolerate node failure; clustering/replication is a separate deployment decision. [Clusters](https://docs.restate.dev/server/clusters).
3. **Retention is part of correctness and diagnosis.** Workflow/idempotency/journal retention controls completed-result access, deduplication lifetime, and inspectable history; defaults are not permanent history. Choose retention for delayed callbacks and real operator response times. [Configuration](https://docs.restate.dev/services/configuration). Upstream can export OpenTelemetry traces and Prometheus metrics, but application correlation and alerts still need integration. [Tracing](https://docs.restate.dev/server/monitoring/tracing), [metrics](https://docs.restate.dev/server/monitoring/metrics).

## Suggested experiment boundary

Inference: a branch experiment with a short per-PR coordinator, a per-attempt workflow, and the existing worker is a useful larger pilot. It exercises durable dispatch/report/deadline ownership without making mutable checkout contents part of replay. Measure removed lifecycle branches and operator recovery work, then require failure tests for ambiguous dispatch, duplicate/stale callbacks, restarts while waiting, cancellation with a live provider job, competing legacy dispatch, and code deployment during a suspended attempt. The experiment should demonstrate which old mechanisms can actually be deleted; a parallel journal alone does not establish reduced maintenance.
