# 025. MCP tools are Restate handlers, and the Operator object is the refresh authority

**Status:** Proposed
**Date:** 2026-09-17
**References:** ADR 017, ADR 018, ADR 023, AII-687 (parent), AII-707 (`RefreshAuthority` seam, `SqliteRefreshAuthority`), AII-627 (Restate sidecar and ingress), AII-709 (this issue), AII-708 (auth-event measurement), AII-702 (the `"run"` identity kind), `docs/restate.md`, `docs/access-model.md`

## Context

`/mcp`'s identity surface was SQLite end to end: `mcp_tokens` for access-token verification, `mcp_refresh_tokens` for the refresh grant, both read and written inline in `src/mcp-oauth.ts`. AII-707 cut a seam out of that inline logic — `RefreshAuthority` (`src/mcp-identity.ts`) with `issue`, `rotate`, `revokeFamily` — and kept the original SQLite behavior behind it as `SqliteRefreshAuthority`, so `handleMcpTokenRequest` no longer cares which authority answers a refresh grant.

Two problems the seam alone doesn't fix. First, `SqliteRefreshAuthority.rotate` treats every re-presentation of a just-rotated refresh token as theft and revokes the whole family — correct for a genuine replay, wrong for two legitimate callers (two Claude Code sessions sharing one credential store, or a client retrying a dropped response) racing the same rotation. Second, nothing serializes concurrent `rotate` calls for the same family: two requests can both read the pre-rotation row before either writes, defeating the single-use check entirely under real concurrency. Both are lifecycle-state problems — exactly what ADR 017 names as Restate's fit: a durable, single-writer view of one piece of state, with exclusive handlers serializing concurrent callers for free.

ADR 018 names kg-refresh as the first Restate migration and leaves later run kinds and surfaces contingent on that gate. This issue is not a workflow migration — the refresh grant is not a "run" — but it is the same shape of problem (concurrent callers, one piece of durable state, a decision that must not race itself), and Restate's Virtual Object primitive — one instance per key, handlers `exclusive` by default, `ctx.rand`/`ctx.date` in place of a wall clock — fits it directly. `restatedev/ai-examples`' `personObject` is the reference shape: one object per identity, a state table, handlers keyed by that identity.

## Decision

**The MCP identity surface's stateful decisions run as Restate handlers, keyed by OAuth client id, and the refresh grant is the first of them.** `src/restate/operator-object.ts` defines `Operator`, one Virtual Object per client id, with `issue`, `refresh`, and `revoke` as `exclusive` handlers (mutual exclusion is the point — two racing `refresh` calls for the same client must observe each other's writes) and `describe` as `shared` (a read has no reason to queue behind the others). `RestateRefreshAuthority` implements the `RefreshAuthority` seam from AII-707 as a thin ingress HTTP client, and is the default authority as of this release; `SqliteRefreshAuthority` is kept for one release as the rollback path and dropped afterward. `src/mcp.ts`'s tool handlers are unaffected by this issue — they still read and write SQLite directly — but the `Caller`/`IdentityKind` contract in `src/mcp-identity.ts` is written to admit a future Restate-issued `"run"` identity (AII-702) alongside `"human"` and `"system"` without a second rewrite; broadening beyond the refresh grant is future scope, decided when a second stateful MCP surface needs it, not assumed here.

Design points specific to the Operator object:

- **One bounded grace window, not zero tolerance.** `refresh` keeps `currentHash` and one `previousHash` with `rotatedAt`. A presentation of the current hash rotates and returns the new pair. A presentation of the previous hash within `GRACE_MS` (30s, inclusive of the boundary) returns the *same* pair the rotation already produced — the concurrent caller is handed the answer to a rotation that already happened, not treated as a second legitimate rotation. Past the window, it is replay and clears state. An unknown hash is replay but leaves a live family untouched, so a forged or stale presentation cannot be used to wipe out a concurrent, correct caller's state.
- **The object mints the next raw token.** `refresh`'s exclusive handler is the only place a rotation can happen without a caller racing itself, so it has to produce the new raw value via `ctx.rand.uuidv4()`, not receive one. That is the one place a raw token exists inside the object's state (`currentToken`, kept only so a concurrent caller within the grace window gets the identical pair back) — every other path in and out of the object carries a hash, never the raw value, because the ingress journals request and response bodies and a journaled raw token would outlive its own rotation.
- **`RestateRefreshAuthority` never throws.** A connection failure, a non-2xx response, or a non-JSON body from a handler that should return one all resolve to `{ status: "unavailable" }`. A `void` handler (`issue`, `revoke`) answers with an empty body on success — the client treats an empty 200 body as success, not a parse failure, and only a *non-empty* unparseable body maps to `unavailable`.
- **The allowlist re-check stays the revocation path (AII-687 decision, carried from `SqliteRefreshAuthority.rotate`).** After the object answers a successful rotation and before minting the access token, `RestateRefreshAuthority.rotate` re-reads the effective allowlist: an unreadable list defers (`unavailable`, no revocation — a transient read failure is not a removal), and an identity the list no longer admits gets its family revoked through the object's own `revoke` handler and a `denied` outcome. This check runs in `RestateRefreshAuthority`, not inside the object, because the allowlist is a SQLite-backed, poll-refreshed cache (`src/access-entries.ts`) that has no reason to become object state.
- **Auth-event measurement (AII-708) stays populated.** `RestateRefreshAuthority.rotate` emits exactly one `recordAuthEvent({ kind: "refresh", ... })` per call, on every return path, with the same cause vocabulary `SqliteRefreshAuthority.rotate` uses (`ok`, `replay`, `expired`, `unavailable`, `allowlist`) so switching the default authority doesn't blind that dashboard. `familyId` is the client id, since this object is one-per-client rather than one-per-rotation-chain.
- **No fallback authority, and no shadow mode.** When the Restate ingress is down, `POST /mcp/token` answers `503 { error: "restate-unavailable" }` for both grant types — the authorization-code grant's `issue` call fails the same way. There is no code path that falls back to SQLite when Restate is unreachable; the rollback is operational (flip the default back to `SqliteRefreshAuthority`), not automatic, because an automatic fallback would silently reintroduce the zero-grace-window behavior this issue exists to fix.

## Alternatives considered

- **Serialize refreshes with a SQLite lock or transaction instead of a Virtual Object.** Rejected: SQLite already offers atomic reads/writes, but the actual bug is the *policy* (zero grace window), not the isolation level — a correctly serialized version of the old policy still revokes a legitimate concurrent caller. A Virtual Object's exclusive handler buys the serialization for free as a side effect of adopting the grace-window fix, rather than as a second mechanism to maintain.
- **Widen `SqliteRefreshAuthority`'s grace window in place, no Restate.** Rejected: a wider window still needs the same read-then-write-is-atomic guarantee to avoid the double-rotation race, and hand-rolling that (an advisory lock, a busy-retry loop) is exactly the lifecycle glue ADR 017 is trying to stop writing per run kind — here, per stateful MCP surface.
- **Route every MCP tool through Restate now.** Rejected as out of scope for this issue: no other MCP surface has the concurrency problem the refresh grant has, and broadening the `Caller` contract's `"run"` kind ahead of a second concrete need would be speculative. The `IdentityKind` union is shaped to admit it later without cost paid now.
- **A shadow-mode rollout (write to both authorities, compare).** Rejected per the parent issue's decision: the SQLite and Restate behaviors intentionally diverge (grace window vs. none), so shadow comparison would report the fix as a discrepancy on every legitimate concurrent refresh.

## Consequences

Easier: two Claude Code sessions (or a client retrying a dropped response) sharing one refresh token no longer revoke each other's session; the concurrency bug that made that possible is a property SQLite's isolation level didn't give for free and this object does. Auth-event telemetry and the allowlist revocation path are indistinguishable in shape from the SQLite era, so AII-708's dashboards and the access-model's fail-closed guarantee (`docs/access-model.md`) carry over unchanged.

Harder: the refresh grant now has a hard dependency on the Restate sidecar being up — a dependency `verifyMcpToken` and every other SQLite-backed MCP path does not share, so an outage narrows to "nobody can refresh" rather than "nobody can use MCP." `SqliteRefreshAuthority` stays in the tree for exactly one release as the rollback switch; a later cleanup issue deletes it and the `mcp_refresh_tokens` table together.

Open for a later decision, not this one: if a second MCP surface needs durable per-identity state, whether it gets its own Virtual Object or joins `Operator`'s state table is a call for that issue, against whatever its own concurrency shape turns out to be.

## Amendment (2026-09-17): the write tools are request-scoped handlers, not durable workflows

**Context.** The review of the integrated feature branch (PR #603, AII-717) found that the six write handlers call their admin action functions outside `ctx.run`. A Restate invocation outlives the process that started it: the journal lives on the data volume, the sidecar restarts with the orchestrator, and `register()` runs before the first poll. An attempt that died with the orchestrator mid-write was therefore re-delivered after the reboot, and the action ran a second time. That is the one path on this branch where the Restate layer could reach a pipeline table twice. The in-process tools never had this property: their request died with the process.

**Decision.** Each write handler declares `retryPolicy: { maxAttempts: 1, onMaxAttempts: "kill" }`, so an attempt that fails for any reason is killed and never re-delivered. This restores the request-scoped behaviour the in-process tools had, by construction. Independently, every side effect inside a handler runs in `ctx.run` with `RunOptions { maxRetryAttempts: 1 }`: a thrown action surfaces as a `TerminalError` the `tool()` wrapper already converts to an `isError` result, and a replayed attempt (the `alwaysReplay` test variant) returns the journaled result instead of re-running the action. The two settings answer two questions: the retry policy decides whether an attempt can run again; `ctx.run` decides what a replayed attempt does with a step that already ran.

**Alternatives rejected.** `ctx.run` alone keeps the write durable but leaves a millisecond window between the SQLite commit and the journal commit in which a crash re-runs the action. A try/catch inside the `ctx.run` closure to preserve the error text is a mechanism of our own that `RunOptions` already provides. A new ADR was not warranted: the decision is one line per handler and reversible.

**Consequences.** The write tools are not durable. That is acceptable: every caller is synchronous, sees the result, and repeats a failed call by hand. The "durable handlers" wording in the ADR 015 amendment and in AII-713 is superseded by this paragraph. When a workflow later owns one of these writes (ADR 018), the workflow's own steps carry the durability; the tool handler keeps its request-scoped policy. A killed invocation that carried an idempotency key holds that key's result as the failure, so a caller that wants to try again supplies a new key (AII-719 makes the key caller-supplied).
